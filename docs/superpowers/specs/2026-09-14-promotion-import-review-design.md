# Promotion Import and Review Design

## Goal

Collect promotion information from official LINE Pay, JKO Pay, and iPASS MONEY
pages without allowing unreviewed extraction results to affect payment
recommendations. An administrator reviews each imported promotion and publishes
only verified rules into the existing catalog.

## Scope

This feature adds:

- Source-specific import adapters for LINE Pay, JKO Pay, and iPASS MONEY.
- A command-line import job that creates auditable import runs and promotion
  drafts.
- Admin APIs and UI for reviewing, rejecting, and publishing drafts.
- A publish path that creates a regular `RewardRule` only after its merchant,
  payment method, and acceptance mapping have been verified.

This feature does not add automated publishing, account authentication, browser
automation, or generic extraction based on LLM output.

## Architecture

The importer is a separate CLI process. It does not run in an Express request
and cannot block API availability. The job accepts one source at a time:

```text
npm run import:promotions -- --source line-pay
npm run import:promotions -- --source jko-pay
npm run import:promotions -- --source ipass-money
```

Each source adapter implements a shared interface that fetches its official
public pages and returns a normalized list of candidate promotions. The shared
import service persists the run and its drafts. Adapters are responsible only
for source retrieval and extraction; they never create merchants, payment
methods, acceptance mappings, or reward rules.

```text
Official source page
  -> source adapter
  -> normalized candidate promotion
  -> ImportRun + PromotionDraft
  -> Admin review
  -> RewardRule
  -> public recommendation
```

## Data Model

`ImportRun` records one import attempt:

| Field | Meaning |
|---|---|
| `id` | Database identifier |
| `source` | `line-pay`, `jko-pay`, or `ipass-money` |
| `status` | `running`, `completed`, or `failed` |
| `startedAt`, `completedAt` | Execution timing |
| `errorMessage` | Failure detail when the source could not be imported |
| `draftCount` | Number of drafts generated by the run |

`PromotionDraft` records an independently reviewable source item:

| Field | Meaning |
|---|---|
| `id`, `importRunId` | Identity and import provenance |
| `source`, `sourceUrl`, `sourceTitle` | Official-source attribution |
| `sourceContent` | Captured text needed for a reviewer to validate extraction |
| `sourceFingerprint` | Stable hash of source and canonical activity identity |
| `fetchedAt` | Time the item was retrieved |
| `parsedCashbackRate`, `parsedAmountThreshold`, `parsedValidityStart`, `parsedValidityEnd` | Optional extracted values |
| `status` | `pending_review`, `published`, or `rejected` |
| `merchantId`, `paymentMethodId` | Verified catalog mapping selected during review |
| `rewardRuleId` | Rule created by publishing |
| `reviewedAt`, `rejectionReason` | Review audit data |

`sourceFingerprint` is unique per source activity. A repeat import updates only
an existing `pending_review` draft's captured source data and parsed values. It
does not modify published or rejected drafts, so review history stays stable.

## Import Behavior

The job creates an `ImportRun` with `running` status before fetching. It marks
the run `completed` with its draft count only after all persistence succeeds.
If fetching, parsing, or persistence fails, it marks the run `failed` with a
safe error message and exits non-zero.

Parsing is deliberately conservative. An adapter may emit a draft with no
parsed cashback rate, threshold, or dates when the official page cannot be
reliably interpreted. The captured source fields are still useful to the
reviewer. A parsing failure must never publish a reward rule.

The job sends a normal identifiable user agent, observes each official site's
published terms and rate limits, and makes no attempt to bypass access controls,
CAPTCHAs, login requirements, or robots restrictions. Sources that cannot be
retrieved under these constraints fail visibly and remain unsupported until a
permitted source mechanism exists.

## Admin Review

Authenticated Admin APIs expose:

- `GET /api/admin/import-runs`
- `GET /api/admin/promotion-drafts?status=pending_review`
- `PATCH /api/admin/promotion-drafts/:id` to save verified fields and catalog
  mappings while still pending
- `POST /api/admin/promotion-drafts/:id/publish`
- `POST /api/admin/promotion-drafts/:id/reject`

The Admin page adds an **Imported promotions** section. It shows the source,
URL, captured text, parsed values, run status, and draft status. For each
pending draft the reviewer can:

1. Choose existing merchant and payment method catalog records.
2. Add the acceptance mapping through the existing catalog controls if needed.
3. Correct cashback rate, amount threshold, dates, and promotion note.
4. Publish or reject with a required rejection reason.

Publishing validates that the draft is still pending, its mapping and all
reward fields are present and valid, and the selected payment method is
accepted by the merchant. It uses a transaction to create the reward rule and
mark the draft published together. A failed validation leaves the draft
pending. A published or rejected draft cannot be published again.

## Error Handling

All source failures are confined to their `ImportRun`; existing rules and
drafts from other sources are untouched. API validation errors return `400`,
missing drafts return `404`, and conflicting state transitions or dependent
catalog relationships return `409`. Source content is rendered in Admin UI
using HTML escaping, and source URLs are restricted to `https:` before becoming
clickable links.

## Testing

Tests cover:

- Import-run status transitions and source-specific adapter normalization using
  saved fixture content, without live network calls.
- Idempotent handling of a repeated fingerprint for each draft state.
- Draft API authorization, filtering, validation, rejection, and missing IDs.
- Publish validation, atomic creation of a reward rule, and enforcement of the
  existing merchant-acceptance invariant.
- CLI source selection, success exit behavior, and failed run recording.
- Admin UI syntax plus draft rendering and submission behavior where practical.

## Deployment Notes

The import job is manually run in the initial beta. Scheduling, credentials,
and automated retries are explicitly deferred. Production deployment must run
the API and importer with the same database configuration, but only the API
needs to be publicly reachable.
